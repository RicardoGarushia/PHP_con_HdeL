# 85. PRINCIPIO DE RESPONSABILIDAD ÚNICA (SRP) Y DEFINICIÓN DE RESPONSABILIDADES EN SOFTWARE

El **PRINCIPIO DE RESPONSABILIDAD ÚNICA** (_Single Responsibility Principle_ - **SRP**), que representa la **"S"** del famoso acrónimo **SOLID**, establece que:

> _"Una clase, módulo o archivo debe tener una, y solo una, razón para cambiar."_

En términos sencillos: **cada archivo en tu proyecto debe tener un único trabajo bien definido**. Si necesitas modificar un archivo por dos motivos completamente diferentes (por ejemplo, porque cambió la regla del cálculo de impuestos Y porque cambió el formato de respuesta JSON), ese archivo está asumiendo más de una responsabilidad.

---

## 85.1. ¿POR QUÉ ES CRUCIAL DEFINIR RESPONSABILIDADES?

Cuando los archivos asumen múltiples roles, el código se vuelve frágil, difícil de probar y complejo de mantener. Aplicar una estricta definición de responsabilidades aporta los siguientes beneficios:

1. **Bajo Acoplamiento y Alta Cohesión:** Modificar la interfaz gráfica no rompe la lógica de base de datos, y cambiar una consulta SQL no afecta las validaciones.
2. **Mantenibilidad:** Sabes exactamente a qué archivo ir cuando surge un error o un nuevo requerimiento.
3. **Facilidad de Pruebas (Testing):** Es infinitamente más sencillo probar una función o clase pequeña que realiza una sola tarea que probar una función gigante de 300 líneas.
4. **Reutilización:** Los componentes especializados pueden volver a usarse en distintas partes de la aplicación sin arrastrar dependencias innecesarias.

---

## 85.2. LA CADENA DE RESPONSABILIDADES EN EL ECOSISTEMA DE LARAVEL

Para visualizar cómo se traduce este principio al desarrollo práctico con MVC y arquitecturas modernas en Laravel, observemos el rol específico de cada componente:

```
[ Petición HTTP ]
       │
       ▼
┌──────────────────────────────┐
│ 1. Form Request              │ ──> Validar y autorizar la entrada de datos.
└──────────────┬───────────────┘
               │
               ▼
┌──────────────────────────────┐
│ 2. Controller                │ ──> Orquestar el flujo (recibir, delegar, responder).
└──────────────┬───────────────┘
               │
               ▼
┌──────────────────────────────┐
│ 3. Service Class             │ ──> Ejecutar la lógica de negocio (Dominio Puro).
└──────────────┬───────────────┘
               │
               ▼
┌──────────────────────────────┐
│ 4. Eloquent / Repository     │ ──> Interactuar con la base de datos (Persistencia).
└──────────────┬───────────────┘
               │
               ▼
┌──────────────────────────────┐
│ 5. View / Blade / API Res.   │ ──> Formatear y presentar la información al usuario.
└──────────────────────────────┘
```

## 85.3. DESGLOSE DE ROLES POR ARCHIVO

### 🛡️ 1. Form Requests (`app/Http/Requests`)

- **Única Responsabilidad:** **Validación y Autorización.**
- **Qué hace:** Comprueba que los datos recibidos del usuario sean válidos (`required`, `email`, `numeric`, `max:255`) y que el usuario tenga permiso para realizar la solicitud.
- **Lo que NO debe hacer:** No debe procesar lógica de negocio, ni hacer cálculos, ni realizar inserciones en la base de datos.
- **Ejemplo:** `RegistrarUsuarioRequest`, `CrearProductoRequest`.

### 🎛️ 2. Controladores (`app/Http/Controllers`)

- **Única Responsabilidad:** **Orquestación y Gestión de la Petición/Respuesta HTTP.**
- **Qué hace:** Actúa como un "director de tráfico". Recibe la petición limpia del Form Request, llama a las clases necesarias (Services/Repositories) y retorna la respuesta adecuada (una vista Blade, una redirección o una respuesta JSON).
- **Lo que NO debe hacer:** No debe contener bucles complejos, ni algoritmos de negocio, ni consultas SQL directas.
- **Ejemplo:** `UsuarioController@store` solo toma los datos validados, se los pasa al `UsuarioService` y redirige al dashboard.

### 🧠 3. Service Classes (`app/Services`)

- **Única Responsabilidad:** **Ejecución de la Lógica de Negocio (Dominio).**
- **Qué hace:** Procesa las reglas esenciales del sistema en PHP puro (por ejemplo, calcular la tasa de un préstamo, generar una factura en PDF, comunicarse con una pasarela de pagos externa).
- **Lo que NO debe hacer:** No debe depender de clases HTTP (`Request`, `Response`), ni gestionar redirecciones web.
- **Ejemplo:** `CalculoImpuestosService`, `ProcesarPagoService`.

### 🗄️ 4. Modelos Eloquent y Repositorios (`app/Models` / `app/Repositories`)

- **Única Responsabilidad:** **Persistencia e Interacción con la Base de Datos.**
- **Qué hace:** Representar las tablas de la base de datos, definir sus relaciones (`hasMany`, `belongsTo`), scopes de búsqueda y ejecutar operaciones de lectura/escritura (CRUD).
- **Lo que NO debe hacer:** No debe decidir si un cliente es elegible para una promoción; solo almacena y consulta datos.
- **Ejemplo:** `User`, `OrderRepository`.

### 🖥️ 5. Vistas y Formateadores (`resources/views` / `app/Http/Resources`)

- **Única Responsabilidad:** **Presentación de Datos.**
- **Qué hace:** Renderizar el HTML/Blade o transformar arrays/JSON para la interfaz de usuario. Su único trabajo es mostrar la información de forma clara e interactiva.
- **Lo que NO debe hacer:** No debe realizar consultas a la base de datos dentro de la plantilla (`@php User::all() @endphp`), ni ejecutar operaciones matemáticas complejas.

## 85.4. SÍNTOMAS DE QUE ESTÁS VIOLANDO EL PRINCIPIO DE RESPONSABILIDAD ÚNICA

Sabrás que un archivo está asumiendo demasiadas responsabilidades si detectas cualquiera de estos "olores de código" (_code smells_):

1. **Lógica de base de datos en las Vistas:** Hacer consultas directas dentro de un archivo `.blade.php`.
2. **Validación manual en el Controlador:** Tener decenas de líneas con `$request->validate([...])` en medio de la acción del controlador.
3. **Cálculos de negocio en los Modelos:** Tener un modelo de Eloquent con métodos gigantescos que envían correos electrónicos, generan archivos y calculan nóminas.
4. **Dependencias HTTP en la Capa de Servicio:** Pasar la variable `$request` completa a una Service Class.

---

## 85.5. CONCLUSIÓN

El **Principio de Responsabilidad Única** no se trata solo de escribir archivos más cortos, sino de construir un sistema modular donde cada componente hace una sola cosa y la hace bien.

Al aplicar esta separación de responsabilidades:

- Si cambia el **diseño de la interfaz**, solo tocas la **Vista**.
- Si cambian las **reglas de validación**, solo tocas el **Form Request**.
- Si cambian los **criterios del negocio**, solo tocas el **Service**.
- Si cambia la **estructura de la base de datos**, solo tocas el **Modelo/Migración**.

Esta modularidad es la base para construir aplicaciones escalables, mantenibles y profesionales.

---

> 💡 **Nota de Arquitectura Avanzada: Las Interfaces y el Desacoplamiento (Inversión de Dependencias)**
>
> Aunque el Principio de Responsabilidad Única (SRP) nos enseña a separar tareas en archivos distintos, el uso de **Interfaces** ayuda a que estos componentes no dependan directamente unos de otros.
>
> - **Concepto Clave:** Una interfaz es un contrato formal (`interface`) que define _qué_ métodos se deben implementar sin especificar _cómo_.
> - **Clases Implementadoras:** Escriben el código concreto de la lógica (ej. `SmsService` o `EmailService`).
> - **Clases Consumidoras:** Solicitan la interfaz en lugar de una clase concreta para ejecutar la acción sin acoplarse a una tecnología específica.
> - **En Laravel:** Las interfaces se llaman **Contracts** (`Illuminate\Contracts\...`). El framework utiliza su **Service Container** para inyectar automáticamente la clase implementadora configurada en los **Service Providers** (`AppServiceProvider.php`), permitiendo cambiar de proveedor o tecnología modificando una sola línea de código.
