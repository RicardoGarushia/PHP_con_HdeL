# 31. POO: Interfaces y Desacoplamiento (Principio de Inversión de Dependencias (DIP))

Una **interfaz** es una estructura que define un conjunto de métodos públicos OBLIGATORIOS que cualquier clase TIENE QUE implementar si se compromete a ello mediante la palabra clave `implements`.

Es decir, una interfaz actúa como un **CONTRATO**, dado que cualquier clase que implemente dicha interfaz se compromete a definir todos sus métodos.

A diferencia de las clases abstractas (véase _030.ClasesAbstractas.md_), las interfaces no aportan reutilización de código ni lógica interna; únicamente estipulan el **QUÉ** debe hacer un componente, desentendiéndose por completo del **CÓMO**.

---

## 31.1. Pilares del Diseño orientados a Interfaces

La funcionalidad principal de las interfaces se centra en tres pilares del diseño de software:

1. **Abstracción:** Oculta los detalles de implementación interna de cada proveedor de servicio. Define el **QUÉ** se debe hacer (el contrato), ocultando el **CÓMO** se hará (la implementación concreta). El módulo (clase o función) consumidor interactúa con una firma estandarizada sin necesitar conocer la complejidad interna de cada clase.
2. **Polimorfismo:** Permite que objetos de diferentes clases sean tratados exactamente de la misma manera si implementan la misma interfaz.
3. **Desacoplamiento:** Rompe la dependencia directa entre clases. La clase de alto nivel depende de la interfaz, no de la clase concreta. Es decir, permite sustituir, probar o extender componentes del sistema sin modificar la clase que los consume.

El objetivo de las interfaces es establecer una **ESTRUCTURA COMÚN ENTRE CLASES NO RELACIONADAS** al forzar a dichas clases a implementar ciertos métodos. Esto se conoce como **PROGRAMACIÓN ORIENTADA A INTERFACES** y es fundamental para la flexibilidad y el desacoplamiento del código.

### 31.2. Principio de Inversión de Dependencias (DIP)

Las interfaces son el pilar fundamental para aplicar la **D** de los principios **SOLID**: el **Principio de Inversión de Dependencias (Dependency Inversion Principle - DIP)**.

> **Conceptos Clave**
>
> - **Clases de Alto Nivel (Consumidores/Clientes):** Contienen la lógica de negocio principal y no deben depender de módulos de bajo nivel.
> - **Clases de Bajo Nivel (Servicios/Proveedores):** Ejecutan tareas operativas específicas (guardar en base de datos, enviar correos, escribir archivos).

- **Principio de Inversión de Dependencias (DIP):** Establece que los módulos o clases de alto nivel (el "cliente" o consumidor) no deben depender de módulos o clases de bajo nivel (el "servicio" o proveedor). Ambos deben depender de **abstracciones** (interfaces). Además, las abstracciones no deben depender de los detalles, sino que los detalles deben depender de las abstracciones.
- **Implementación práctica:** Esto se logra típicamente mediante la **Inyección de Dependencias por Constructor**, pasando el objeto de la clase implementadora como argumento del constructor de la clase consumidora. De este modo, la clase de alto nivel queda totalmente liberada del control sobre la infraestructura de almacenamiento.

## 31.3. Diferencias Técnicas: Clase Abstracta vs. Interfaz

| Característica             | Clase Abstracta                                         | Interfaz                                                              |
| :------------------------- | :------------------------------------------------------ | :-------------------------------------------------------------------- |
| **Instanciación**          | No instanciable (`new` prohibido)                       | No instanciable (`new` prohibido)                                     |
| **Relación Jerárquica**    | Herencia simple (`extends`) — Expresa _"Es un/a"_       | Múltiple implementación (`implements A, B`) — Expresa _"Puede hacer"_ |
| **Contenido de Métodos**   | Métodos concretos (con cuerpo) y abstractos             | Exclusivamente firmas de métodos abstractos                           |
| **Visibilidad de Métodos** | `public`, `protected` o `private`                       | Estrictamente `public`                                                |
| **Atributos y Estado**     | Admite propiedades de instancia, estáticas y constantes | Únicamente permite constantes de clase (`const`)                      |
| **Constructores**          | Puede definir `__construct()` para clases hijas         | No permite constructores                                              |

### 31.3.1. Criterio de Selección: Clase Abstracta vs. Interfaz

- Utiliza **Clases Abstractas** cuando exista una relación de parentesco directa entre clases que compartan estado o lógica reusable.
- Utiliza **Interfaces** cuando requieras definir contratos de comportamiento común entre clases completamente heterogéneas o no relacionadas.

---

## 31.3. Sintaxis de la interfaz

La declaración empleará la palabra reservada `interface`. Todos los métodos especificados omiten el cuerpo `{}` y finalizan en punto y coma `;`:

```php
<?php
interface NombreDeLaInterface
{
    public function metodo1(datatype $parametro1, datatype $parametro2): datatypeRetorno;
    public function metodo2(datatype $parametro1): datatypeRetorno;
    public function metodoN(): datatypeRetorno;
}
```

## 31.4. Ejemplo práctico de interfaz

```php
<?php
declare(strict_types=1);

header("Content-Type: text/plain; charset=utf-8");

echo "======================================================================\n";
echo "31. POO: Interfaces y Desacoplamiento\n";
echo "======================================================================\n\n";

// --- INTERFACES (Contratos) ---

// Definición de la interfaz EnviarDatos (Interfaz A)
interface EnviarDatos
{
    public function enviar(string $message): void; // Función A de Interfaz A
}

// Definición de la interfaz GuardarDatos (Interfaz B)
interface GuardarDatos
{
    public function guardar(): void; // Función A de Interfaz B
}

// --- CLASES IMPLEMENTADORAS ---

// CLASE IMPLEMENTADORA #1: Implementa ambas interfaces
class Servidor implements EnviarDatos, GuardarDatos
{
    public function enviar(string $message): void
    {
        echo "Se envía la venta del SERVIDOR al jefe\n" . $message . "\n";
    }

    public function guardar(): void
    {
        echo "Se guarda la venta en el SERVIDOR\n";
    }
}

// CLASE IMPLEMENTADORA #2: Solo implementa GuardarDatos
class Nube implements GuardarDatos
{
    public function guardar(): void
    {
        echo "Se guarda la venta en LA NUBE\n";
    }
}

// CLASE IMPLEMENTADORA #3: Solo implementa EnviarDatos
class Email implements EnviarDatos
{
    public function enviar(string $message): void
    {
        echo "Se envía la venta por EMAIL al jefe\n" . $message . "\n";
    }
}

// --- CONSUMIDORES (Dependen de la abstracción) ---

// CLASE CONSUMIDORA #1: Recibe un objeto que implemente la interfaz GuardarDatos
class ProcesadorDeDatos
{
    // Propiedad que almacena una instancia de cualquier clase que implemente GuardarDatos
    private GuardarDatos $guardado;

    // Inyección de dependencias por Constructor
    public function __construct(GuardarDatos $procesoDeGuardado)
    {
        $this->guardado = $procesoDeGuardado;
    }

    public function procesar(): void
    {
        echo "Procesando la información mediante la CLASE consumidora\n";
        $this->guardado->guardar();
    }
}

// FUNCIÓN CONSUMIDORA #1: Recibe un objeto que implemente la interfaz GuardarDatos
function ProcesarDatos(GuardarDatos $objeto): void
{
    echo "Procesando la información mediante la FUNCIÓN consumidora\n";
    $objeto->guardar();
}

// --- EJECUCIÓN ---
$servidor = new Servidor(); // Implementa ambas interfaces: EnviarDatos y GuardarDatos
$nube     = new Nube();     // Solo implementa la interfaz GuardarDatos
$email    = new Email();    // Solo implementa la interfaz EnviarDatos

// Creación del objeto ProcesadorDeDatos con Inyección de Dependencias
$guardado = new ProcesadorDeDatos(procesoDeGuardado: $servidor);    // Intercalar entre $nube y $servidor. $email produce error por no tener implementado el método procesar() y no ser del tipo GuardarDatos
$guardado->procesar();

echo "\n----------------------------------------------------------------------\n";

// Ejecución de la función consumidora
ProcesarDatos(objeto: $email);  // Intercalar entre $nube y $servidor. $email produce error por no tener implementado el método procesar() y no ser del tipo GuardarDatos
```
